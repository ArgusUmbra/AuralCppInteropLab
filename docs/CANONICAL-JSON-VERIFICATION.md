# Internal canonical JSON byte verification

`src/core/json/canonical_json_verifier.hpp` is an internal, experimental C++20
API. It accepts a borrowed byte span and reports whether those exact bytes are
already the RFC 8785 representation of the JSON value they encode. It is not
installed as public `libaural` surface and has no stable API or ABI promise.

Canonicality is only a byte-representation property. A canonical result does
not establish AURAL manifest semantics, complete package validity, evidence
authenticity, cryptographic provenance, or signature validity.

## Algorithm and ownership

The verifier first enforces the 1,048,576-byte on-disk JSON ceiling. It then
uses the existing strict complete-document parser, including its UTF-8,
Unicode-scalar, forbidden-noncharacter, duplicate-decoded-name, safe-integer,
depth, value-count, and aggregate decoded-string checks. A successful owned
parse tree is passed unchanged to the existing complete canonical serializer.
The verifier compares the borrowed input and temporary canonical output from
byte zero, then compares their lengths. If one is a prefix of the other, the
first mismatch offset is the common length.

The caller's bytes are never modified and regenerated bytes are never exposed
by this API. Parse or serialization failure returns no canonical or
noncanonical success detail. In particular, the component never repairs or
rewrites its input.

## Result taxonomy

`JsonCanonicalityResult` has four mutually exclusive statuses:

- `canonical`: the lengths and every byte match;
- `invalid_document`: syntax, Unicode, duplicate-name, or AURAL number-profile
  rejection, with the existing parser or serializer detail;
- `noncanonical`: a valid in-profile document whose bytes differ, with the
  first differing byte offset; and
- `resource_failure`: input, depth, value-count, decoded-string, temporary
  output, allocation, or defensive internal-serialization exhaustion.

Messages name the failed rule or bounded resource without echoing the source
document. Parser and serializer details retain deterministic offsets and value
context where applicable.

## Bounds

The verifier uses the established hard ceilings: 1,048,576 source bytes,
container depth 32, 1,048,576 values, and 1,048,576 aggregate decoded string
and property-name bytes. Its temporary canonical serialization uses the
separate 33,554,432-byte ceiling. Canonical output is not assumed to be shorter
than input. The reused parser and serializer use checked arithmetic, bounded
allocation, iterative traversal, and exact pre-measurement before output
allocation. Allocation and container length failures are converted to typed
resource failures at this `noexcept` boundary.

## Test coverage

`core_json_canonicality` is registered with CTest and therefore with the Linux
GCC, Clang, and Clang ASan/UBSan workflow presets. Expected canonical bytes and
mismatch offsets are stated independently of the verifier. Tests cover roots,
containers, nesting, UTF-16 property order, escaping, safe-integer boundaries,
the exact input/depth limits, noncanonical but valid encodings, strict parser
rejections, deterministic results, source immutability, failure-result shape,
and the frozen public golden manifest. The golden fixture is first compared
directly against an independently specified canonical byte constant.
